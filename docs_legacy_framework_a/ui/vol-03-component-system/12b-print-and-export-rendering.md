## 12B.1 Print and Export Philosophy

ERP systems live and die by their printed output. A purchase order emailed to a Mombasa supplier, a payslip handed to a Nairobi employee, a KRA eTIMS-compliant tax invoice attached to a delivery — these are not secondary features; they are primary business deliverables. AwoERP's print and export system treats printable surfaces as first-class citizens of the same SDUI pipeline that serves interactive screens.

The core principle is **one definition, two renderings**: a surface marked as printable defines its layout once in the AST, and the system produces both an interactive screen view and a printer-friendly output from the same definition. Print-specific layout adjustments (header/footer bands, page breaks, column widths) are expressed as print-mode variants on existing nodes, not as entirely separate surface definitions.

All PDF generation happens server-side in the Go backend. There is no dependency on browser print APIs for the canonical PDF output, ensuring consistent rendering across all tenants, all devices, and all screen sizes. Browser print is available as a lightweight fallback for users who want immediate output, but the server-side pipeline is authoritative for archival and compliance purposes.

> **✅ Convention:** Every document that must comply with KRA eTIMS regulations — tax invoices, credit notes, debit notes — must be generated by the server-side PDF pipeline. Browser-generated PDFs are not accepted as eTIMS-compliant output because they cannot guarantee the mandatory field layout and QR code placement required by KRA.

## 12B.2 Printable Surface Type

### 12B.2.1 Declaring a Surface as Printable

A surface is declared printable by setting `printable: true` in its surface definition and providing a `print_config` block:

```json
{
  "surface_id": "finance.invoice.view",
  "title": "Invoice",
  "printable": true,
  "print_config": {
    "page_size": "A4",
    "orientation": "portrait",
    "margin": { "top": "15mm", "right": "10mm", "bottom": "15mm", "left": "10mm" },
    "dpi": 150,
    "include_backgrounds": true,
    "footer_height": "20mm",
    "header_height": "35mm"
  },
  "body": [ /* ... screen layout ... */ ],
  "print_body": [ /* ... print layout ... */ ]
}
```

The `print_body` array is an optional alternative layout used when generating PDF output. If `print_body` is absent, the standard `body` layout is used with print-mode CSS applied. For complex ERP documents like invoices, providing a dedicated `print_body` is strongly recommended because screen and print layouts often differ significantly.

### 12B.2.2 Print vs. Screen Layout Variants

Nodes in a print surface can carry a `display_modes` prop that controls their visibility:

```json
{
  "type": "container",
  "display_modes": ["print"],
  "children": [
    { "type": "tpl", "tpl": "Page {{page.current}} of {{page.total}}" }
  ]
}
```

| `display_modes` value | Behaviour |
|-----------------------|-----------|
| `["screen", "print"]` | Visible in both (default) |
| `["screen"]` | Screen only — hidden in PDF |
| `["print"]` | Print only — not rendered in interactive view |

Interactive elements (buttons, filters, pagination controls) are automatically excluded from print output by the PDF pipeline — they are not rendered even if `display_modes` is not explicitly set.

### 12B.2.3 Header / Footer Bands in Print Mode

Multi-page documents need persistent header and footer bands. These are declared in the `print_config.header_template` and `print_config.footer_template` using template references:

```json
{
  "print_config": {
    "header_template": "finance.invoice-print-header",
    "footer_template": "finance.invoice-print-footer",
    "header_height": "35mm",
    "footer_height": "20mm"
  }
}
```

The header template receives page-level variables (`page.current`, `page.total`, `document.title`, `tenant.logo_url`). The footer is typically used for page numbering, document reference, and legal disclaimer text.

```json
{
  "template_key": "finance.invoice-print-footer",
  "body": {
    "type": "container",
    "className": "print-footer",
    "children": [
      { "type": "tpl", "tpl": "{{tenant.legal_name}} | PIN: {{tenant.kra_pin}} | {{tenant.address}}" },
      { "type": "tpl", "tpl": "Page {{page.current}} of {{page.total}}", "className": "page-number" }
    ]
  }
}
```

## 12B.3 PDF Generation from UI Definitions

### 12B.3.1 Server-Side PDF Pipeline (Go → chromedp / wkhtmltopdf)

The server-side PDF pipeline follows these stages:

1. **Surface compilation**: The `UICompilationService` compiles the print surface for the requesting user's `ViewContext`, resolving templates, slots, and permissions.
2. **Data hydration**: The compiled surface's data sources are evaluated, fetching the document data from the appropriate module APIs.
3. **HTML rendering**: The hydrated surface AST is converted to a standalone HTML document using the `PrintHTMLRenderer`.
4. **PDF generation**: The HTML document is fed to chromedp (headless Chrome) or wkhtmltopdf depending on tenant configuration and document type.
5. **Post-processing**: eTIMS QR code injection, watermark application, tenant letterhead injection.
6. **Delivery**: The PDF is either streamed directly to the client or stored in object storage for async retrieval.

```go
// internal/core/ui/pdf/pipeline.go

type PDFPipeline struct {
    compiler     *UICompilationService
    htmlRenderer *PrintHTMLRenderer
    generator    PDFGenerator  // chromedp or wkhtmltopdf
    storage      ObjectStorage
    etims        *ETIMSService
    audit        AuditService
}

func (p *PDFPipeline) Generate(ctx context.Context, req PDFRequest) (*PDFResult, error) {
    span, ctx := trace.StartSpan(ctx, "pdf.generate")
    defer span.End()

    // 1. Compile surface in print mode
    viewCtx := req.ViewContext
    compiled, err := p.compiler.CompileForPrint(ctx, req.SurfaceID, viewCtx)
    if err != nil {
        return nil, fmt.Errorf("compile surface: %w", err)
    }

    // 2. Render to HTML
    html, err := p.htmlRenderer.Render(ctx, compiled, req.DocumentData)
    if err != nil {
        return nil, fmt.Errorf("render html: %w", err)
    }

    // 3. Generate PDF
    pdf, err := p.generator.Generate(ctx, html, compiled.PrintConfig)
    if err != nil {
        return nil, fmt.Errorf("generate pdf: %w", err)
    }

    // 4. Post-process (eTIMS QR, watermark, letterhead)
    pdf, err = p.postProcess(ctx, pdf, req)
    if err != nil {
        return nil, fmt.Errorf("post-process: %w", err)
    }

    // 5. Audit
    p.audit.Record(ctx, audit.Event{
        Type:       "document.exported",
        ActorID:    viewCtx.UserID,
        TenantID:   viewCtx.TenantID,
        ResourceID: req.DocumentID,
        Metadata:   map[string]any{"format": "pdf", "surface": req.SurfaceID},
    })

    return &PDFResult{Content: pdf, ContentType: "application/pdf"}, nil
}
```

chromedp is the preferred generator for complex layouts (invoice, payslip) that rely on CSS features like flexbox and grid. wkhtmltopdf is available as a fallback for simpler documents on constrained environments.

### 12B.3.2 Client-Side PDF (Browser Print API / jsPDF)

For immediate user-initiated prints (e.g. "Print this screen"), AwoERP provides a lightweight client-side print path using the browser's native `window.print()` API. This path uses the same `display_modes` mechanism and a `@media print` CSS block injected by `awo-overrides.css`:

```css
@media print {
  .awo-screen-only { display: none !important; }
  .awo-print-only  { display: block !important; }
  .cxd-Nav, .cxd-header { display: none !important; }
  body { background: white !important; }
}
```

Client-side PDF is not suitable for eTIMS-compliant output, bulk export, or archival. It is provided only as a convenience feature.

### 12B.3.3 PDF Output Schema

Every PDF generated by the server-side pipeline is described by a `PDFRecord` stored in the `pdf_records` table for audit and retrieval:

```sql
CREATE TABLE pdf_records (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id    UUID NOT NULL REFERENCES tenants(id),
    surface_id   TEXT NOT NULL,
    document_id  UUID,
    document_type TEXT,           -- 'invoice', 'po', 'payslip', etc.
    generated_by UUID REFERENCES users(id),
    generated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    storage_key  TEXT,            -- Object storage key
    file_size    BIGINT,
    etims_signed BOOLEAN DEFAULT FALSE,
    watermarked  BOOLEAN DEFAULT FALSE,
    expires_at   TIMESTAMPTZ      -- NULL for permanent documents
);
```

### 12B.3.4 Page Break Hints in AST

The AST supports `page_break` nodes that instruct the PDF generator to insert a page break at that position:

```json
{
  "type": "page_break",
  "condition": "{{line_items.length > 15}}"
}
```

The `condition` field allows conditional page breaks — for example, only break if the line items exceed 15 rows (otherwise the document fits on one page without a break). Conditions are evaluated during HTML rendering using the document data.

## 12B.4 ERP Print Templates

### 12B.4.1 Invoice / Tax Invoice

The invoice is the most important print template in a Kenyan ERP context because it must comply with KRA eTIMS requirements. The template is declared sealed:

```json
{
  "template_key": "finance.tax-invoice",
  "sealed": true,
  "description": "KRA eTIMS-compliant tax invoice",
  "required_fields": [
    "invoice_number", "invoice_date", "buyer_name", "buyer_pin",
    "seller_name", "seller_pin", "seller_address",
    "line_items", "vat_amount", "total_excl_vat", "total_incl_vat",
    "etims_cu_invoice_number", "etims_qr_url", "etims_timestamp"
  ]
}
```

Key layout sections:
- **Header**: Tenant logo (left), "TAX INVOICE" heading (center), Invoice number and date (right)
- **Seller / Buyer block**: Two-column layout with seller details (including KRA PIN) on left, buyer details on right
- **Line items table**: Item code, description, quantity, unit, unit price (KES), VAT rate, VAT amount, total
- **Totals block**: Sub-total, VAT breakdown by rate (0%, 8%, 16%), total payable in KES
- **eTIMS block**: CU Invoice Number, timestamp, QR code (see Section 12B.9)
- **Payment details slot**: M-Pesa paybill, bank details (tenant-configured, injected via slot)
- **Footer**: Tenant legal name, KRA PIN, physical address, page number

```json
{
  "type": "container",
  "className": "invoice-etims-block",
  "display_modes": ["print"],
  "children": [
    { "type": "tpl", "tpl": "CU Invoice No: <strong>{{document.etims_cu_invoice_number}}</strong>" },
    { "type": "tpl", "tpl": "Verification Time: {{document.etims_timestamp | date:'DD/MM/YYYY HH:mm:ss'}}" },
    { "type": "image", "src": "{{document.etims_qr_url}}", "width": 100, "height": 100, "alt": "eTIMS QR Code" }
  ]
}
```

### 12B.4.4 Payslip

The payslip template complies with Kenya Employment Act requirements for pay statement content. It includes statutory deductions:

```json
{
  "template_key": "hr.payslip",
  "required_fields": [
    "employee_name", "employee_id", "national_id",
    "pay_period", "basic_salary", "allowances",
    "nssf_deduction", "shif_deduction", "sha_deduction",
    "paye_deduction", "net_pay", "employer_nssf_contribution"
  ]
}
```

The payslip shows earnings on the left column (basic, housing allowance, transport allowance, commissions) and deductions on the right (PAYE, NSSF employee, SHIF, SHA, HELB, SACCO loan deductions). Net pay appears prominently at the bottom. Employer contributions (NSSF employer, NHIF employer) are shown separately for clarity.

### 12B.4.5 Statement of Account

The customer account statement supports date range filtering and shows opening balance, all transactions in the period, and closing balance:

```json
{
  "template_key": "finance.statement-of-account",
  "print_config": {
    "page_size": "A4",
    "footer_template": "finance.statement-footer"
  },
  "slots": ["bank_details", "ageing_summary"]
}
```

The ageing summary slot is filled by the Finance module to show 0-30 days, 31-60 days, 61-90 days, and 90+ days overdue buckets — critical for credit control in Kenyan B2B trade.

### 12B.4.6 Picking Slip

The picking slip is a warehouse document listing items to be picked for a sales order. For Kenya fuel stations, it includes bay assignment and meter reading spaces:

```json
{
  "template_key": "inventory.picking-slip",
  "print_config": {
    "page_size": "A5",
    "orientation": "portrait"

```

A5 size is used because picking slips are typically handheld. The template includes a barcode of the sales order number for scanner integration.

## 12B.5 Export Actions

### 12B.5.1 Export to CSV

CSV export is declared as an action on `crud` components:

```json
{
  "type": "crud",
  "api": "GET /api/v1/finance/accounts",
  "headerToolbar": [
    {
      "type": "export-excel",
      "label": "Export CSV",
      "format": "csv",
      "api": "GET /api/v1/finance/accounts/export?format=csv",
      "filename": "accounts-{{now | date:'YYYY-MM-DD'}}.csv"
    }
  ]
}
```

The Go handler for the export endpoint streams CSV directly to the client without buffering the full dataset in memory:

```go
func (h *FinanceHandler) ExportAccounts(c *fiber.Ctx) error {
    tenantID := shared.GetTenantID(c.UserContext())

    c.Set("Content-Type", "text/csv")
    c.Set("Content-Disposition", `attachment; filename="accounts.csv"`)

    writer := csv.NewWriter(c.Response().BodyWriter())
    writer.Write([]string{"Account Code", "Name", "Type", "Balance (KES)", "Currency"})

    return store.WithTenant(c.UserContext(), tenantID, func(q *db.Queries) error {
        return q.StreamAccounts(c.UserContext(), func(acc db.Account) error {
            return writer.Write([]string{
                acc.Code, acc.Name, string(acc.Type),
                formatKES(acc.Balance), acc.Currency,
            })
        })
    })
}
```

### 12B.5.2 Export to Excel (XLSX)

Excel export uses the `excelize` Go library. The export handler generates the XLSX file in memory for moderate datasets (< 50,000 rows). Larger datasets use the Temporal bulk export workflow (see Section 12B.5.4).

```go
import "github.com/xuri/excelize/v2"

func buildAccountsXLSX(accounts []db.Account) ([]byte, error) {
    f := excelize.NewFile()
    sheet := "Accounts"
    f.SetSheetName("Sheet1", sheet)

    headers := []string{"Account Code", "Name", "Type", "Balance (KES)", "Currency"}
    for i, h := range headers {
        cell, _ := excelize.CoordinatesToCellName(i+1, 1)
        f.SetCellValue(sheet, cell, h)
    }
    // Set header style (bold, background)
    style, _ := f.NewStyle(&excelize.Style{
        Font: &excelize.Font{Bold: true},
        Fill: excelize.Fill{Type: "pattern", Color: []string{"#1565C0"}, Pattern: 1},
    })
    f.SetRowStyle(sheet, 1, 1, style)

    for i, acc := range accounts {
        row := i + 2
        f.SetCellValue(sheet, fmt.Sprintf("A%d", row), acc.Code)
        f.SetCellValue(sheet, fmt.Sprintf("B%d", row), acc.Name)
        // ...
    }

    return f.WriteToBuffer()
}
```

### 12B.5.4 Bulk Export Queuing (Temporal Workflow)

Bulk exports of large datasets (invoices for a full year, payslips for all employees) are handled by a Temporal workflow to avoid HTTP timeouts and server memory exhaustion:

```go
// internal/core/export/workflow/bulk_export.go

type BulkExportWorkflow struct{}

type BulkExportParams struct {
    TenantID    uuid.UUID
    ExportType  string  // 'invoices', 'payslips', 'accounts'
    DateFrom    time.Time
    DateTo      time.Time
    Format      string  // 'csv', 'xlsx', 'pdf'
    RequestedBy uuid.UUID
    NotifyEmail string
}

func (w *BulkExportWorkflow) Execute(ctx workflow.Context, params BulkExportParams) error {
    ao := workflow.ActivityOptions{
        StartToCloseTimeout: 30 * time.Minute,
        RetryPolicy:         &temporal.RetryPolicy{MaxAttempts: 3},
    }
    ctx = workflow.WithActivityOptions(ctx, ao)

    var storageKey string
    err := workflow.ExecuteActivity(ctx, activities.GenerateBulkExport, params).Get(ctx, &storageKey)
    if err != nil {
        return fmt.Errorf("generate export: %w", err)
    }

    return workflow.ExecuteActivity(ctx, activities.NotifyExportReady, params.NotifyEmail, storageKey).Get(ctx, nil)
}
```

The user triggers a bulk export from the UI; the system immediately returns a "job started" response with a job ID. The UI polls `GET /api/v1/exports/{job_id}/status` for completion and displays a download link when ready.

## 12B.6 Print Permission Controls

Printing and exporting are governed by specific permissions in the `<module>.documents.print` and `<module>.documents.export` permission space:

| Permission | Grants |
|-----------|--------|
| `finance.invoices.print` | Generate PDF for single invoice |
| `finance.invoices.export` | Bulk export invoices to CSV/XLSX |
| `hr.payslips.print.own` | Employee prints their own payslip |
| `hr.payslips.print.all` | HR admin prints any employee's payslip |
| `procurement.po.print` | Print purchase orders |

The `print.own` vs `print.all` pattern is important for payslips — employees must be able to print their own payslips via the self-service portal without being granted access to all payslips.

```go
// Permission check in the PDF pipeline
func (p *PDFPipeline) checkPrintPermission(ctx context.Context, viewCtx ViewContext, docType string, docOwnerID uuid.UUID) error {
    ownPermission := fmt.Sprintf("hr.%s.print.own", docType)
    allPermission := fmt.Sprintf("hr.%s.print.all", docType)

    hasAll := slices.Contains(viewCtx.Permissions, allPermission)
    hasOwn := slices.Contains(viewCtx.Permissions, ownPermission) && docOwnerID == viewCtx.UserID

    if !hasAll && !hasOwn {
        return &shared.BusinessError{
            Code:    "permission_denied",
            Message: "You do not have permission to print this document",
            Status:  403,
        }
    }
    return nil
}
```

Every printable document can include a tenant letterhead band at the top of the first page. The letterhead is assembled from the tenant's stored branding data (logo, legal name, address, contacts, KRA PIN) and injected via the `platform.print-letterhead` template:

```json
{
  "template_key": "platform.print-letterhead",
  "sealed": true,
  "body": {
    "type": "container",
    "className": "letterhead",
    "children": [
      { "type": "image", "src": "{{tenant.logo_url}}", "height": 60 },
      {
        "type": "container",
        "className": "letterhead-details",
        "children": [
          { "type": "tpl", "tpl": "<strong>{{tenant.legal_name}}</strong>" },

          { "type": "tpl", "tpl": "P.O. Box {{tenant.po_box}}, {{tenant.city}}, Kenya" },
```

The letterhead template is sealed — tenants cannot modify the KRA PIN and VAT REG display, as these are required for tax compliance. Tenants can, however, override the `letterhead_logo_position` parameter (left/center/right) and the `letterhead_accent_color`.

## 12B.9 KRA eTIMS QR Code Embedding in Print Output

Kenya Revenue Authority's eTIMS (Electronic Tax Invoice Management System) requires that every tax invoice display a QR code that allows buyers and KRA auditors to verify the invoice online. AwoERP integrates with the KRA eTIMS API to sign invoices and obtain the verification QR code.

The eTIMS integration flow for PDF generation:

1. **Invoice saved**: Finance module saves the invoice with status `DRAFT`
2. **eTIMS submission**: `ETIMSService.SubmitInvoice()` sends the invoice to KRA's API
3. **KRA response**: KRA returns `cu_invoice_number`, `verification_url`, and a QR code image URL
4. **Invoice updated**: These fields are stored against the invoice record
5. **PDF generation**: The PDF pipeline reads `etims_qr_url` from the invoice and embeds it

```go
// internal/core/etims/service.go

type ETIMSService struct {
    client  *ETIMSClient
    invoiceRepo InvoiceRepository
}

type ETIMSSubmitResponse struct {
    CUInvoiceNumber string    `json:"cuInvoiceNumber"`
    VerificationURL string    `json:"verificationUrl"`
    QRCodeURL       string    `json:"qrCodeUrl"`
    SignedAt         time.Time `json:"signedAt"`
}

func (s *ETIMSService) SubmitInvoice(ctx context.Context, invoiceID uuid.UUID) (*ETIMSSubmitResponse, error) {
    invoice, err := s.invoiceRepo.GetByID(ctx, invoiceID)
    if err != nil {
        return nil, err
    }

    payload := buildETIMSPayload(invoice)
    resp, err := s.client.Submit(ctx, payload)
    if err != nil {
        return nil, fmt.Errorf("etims submit: %w", err)
    }

    // Persist eTIMS fields to invoice record
    err = s.invoiceRepo.UpdateETIMSFields(ctx, invoiceID, db.UpdateETIMSFieldsParams{
        ETIMSCUNumber:  resp.CUInvoiceNumber,
        ETIMSQRURL:     resp.QRCodeURL,
        ETIMSSignedAt:  resp.SignedAt,
        ETIMSStatus:    "SIGNED",
    })
    return resp, err
}
```

The QR code must appear on every page of a multi-page invoice (not just the last page). This is achieved by including the eTIMS block in the print header template for invoices, ensuring it repeats on each page:

```json
{
  "template_key": "finance.invoice-print-header",
  "body": {
    "type": "container",
    "className": "invoice-header-band",
    "children": [
      { "type": "slot", "name": "letterhead" },
      {
        "type": "container",
        "className": "etims-stamp",
        "display_modes": ["print"],
        "children": [
          { "type": "image", "src": "{{document.etims_qr_url}}", "width": 80, "height": 80 },
          { "type": "tpl", "tpl": "CU: {{document.etims_cu_invoice_number}}" }
        ]
      }
    ]
  }
}
```

> **⚠ Warning:** An invoice PDF generated before eTIMS signing (i.e., before `etims_cu_invoice_number` is populated) must be watermarked "UNVERIFIED" or blocked from generation entirely. Distributing unsigned invoices in Kenya is a KRA compliance violation. The PDF pipeline checks `invoice.etims_status` before generating and returns HTTP 422 with error code `etims_unsigned` if the invoice has not been signed.

> See Chapter 31-B — Audit and Compliance for the full KRA eTIMS compliance requirements for invoice surfaces.
