● Phase N+6C Architecture Review — EntityRepository Migration

  ---
  SQL Inventory Classification

  Ten SQL statements exist after N+6A. Each gets one of three verdicts:
  EntityRepository, DatabaseQuerier, Raw SQL forever.

  ---
  sqlSetTenantContext — SELECT set_tenant_context($1)

  Classification: Framework infrastructure — eliminate from service layer 
  entirely.

  This is not IAM SQL. It is a framework prerequisite that contrib/pgx must
  handle automatically when operating from a pool. IAM calls it explicitly only
  because it holds raw pgx.Tx handles. As repositories absorb those
  transactions, the explicit call disappears from service.go.

  However: WithTx(tx) path is different. When IAM hands a pre-opened pgx.Tx to a
   repo via WithTx, the repo cannot know whether set_tenant_context has already
  been called on that connection. Two options:

  - contrib/pgx calls it again on every WithTx op — safe but redundant
  - contrib/pgx trusts the caller set it — fragile

  Decision for N+6C: wherever IAM opens a transaction manually (credential
  verification, best-effort audit), it still calls sqlSetTenantContext
  explicitly before the first repo.WithTx call. sqlSetTenantContext leaves
  queries.go last — only in N+6D when DatabaseQuerier takes over transaction
  ownership.

  ---
  sqlLookupCredentials — SELECT id, password_hash, status FROM iam_users WHERE 
  email = $1

  Classification: DatabaseQuerier (N+6D). Do NOT touch in N+6C.

  Fatal incompatibility with EntityRepository: password_hash is Sensitive: true.
   The framework strips sensitive fields from repository responses at the API
  boundary. Whether stripping happens inside contrib/pgx or at the handler layer
   is implementation-defined — but the intent is that sensitive fields do not
  travel through normal data paths. A credential lookup that depends on reading
  password_hash cannot go through a standard repository call.

  Secondary issue: this query runs inside the credential verification
  transaction, which is not best-effort. Error semantics are strict.
  EntityRepository abstractions add indirection to error handling that is not
  appropriate here.

  This statement defines the boundary between N+6C and N+6D. It is the primary
  reason *pgxpool.Pool survives into N+6D.

  ---
  sqlUpdateLastLoginAt — UPDATE iam_users SET last_login_at = $1 WHERE id = $2

  Classification: DatabaseQuerier (N+6D). Do NOT touch in N+6C.

  Two blockers:

  Blocker 1 — Hook interference. UserPasswordHasher is registered on
  BeforeUpdate for iam_user. An EntityRepository update — even via BulkUpdate —
  may trigger the hook pipeline. If BulkUpdate fires per-record hooks, each
  invocation would check password_hash, find it absent in the patch, attempt to
  restore from the existing record, and issue an additional GET. For a
  best-effort write in the audit path, this is unacceptable overhead and fragile
   behavior.

  Clarification needed before any migration: does BulkUpdate fire BeforeUpdate
  hooks per record? If the answer is yes, EntityRepository is permanently wrong
  for this statement. If the answer is no, reassess in N+6D.

  Blocker 2 — Field availability. last_login_at may be a system-managed field
  excluded from the writable field set in UserDefinition. If the
  EntityDefinition marks it as ReadOnly: true or simply omits it from the update
   path, repo.Update and BulkUpdate will silently ignore it or return an error.
  Check UserDefinition before attempting migration.

  ---
  sqlInsertSessionRecord — INSERT INTO iam_sessions ...

  Classification: EntityRepository (N+6C). Migrate.

  SessionDefinition exists as a registered entity. No BeforeCreate hook is
  defined on it. The record fields (tenant_id, user_id, token_hash, ip_address,
  device_id, issued_at, expires_at) map cleanly to the entity definition. No
  sensitive fields involved.

  Migration path: sessionRepo.Create(ctx, record). The repo extracts TenantID
  from context for RLS. The best-effort audit transaction currently combining
  this write with others can be split: three independent repo.Create calls are
  acceptable since the entire block is already best-effort.

  If atomicity of the three audit writes is required: use sessionRepo.WithTx(tx)
   after opening a manual transaction and calling set_tenant_context. This
  preserves current semantics exactly.

  ---
  sqlRevokeSessionByHash — UPDATE iam_sessions SET revoked_at = now() WHERE 
  token_hash = $1 AND tenant_id = $2

  Classification: EntityRepository BulkUpdate (N+6C). Migrate — with 
  precondition.

  Precondition: confirm BulkUpdate does NOT fire per-record BeforeUpdate hooks.
  If it does, this statement stays in DatabaseQuerier.

  Assuming precondition holds: sessionRepo.BulkUpdate(ctx, 
  filter.And(filter.Eq("token_hash", hash), filter.Eq("tenant_id", tenantID)), 
  driver.Patch{Fields: {"revoked_at": time.Now()}}).

  One concern: token_hash must be a queryable field in SessionDefinition. If it
  is Hidden: true or excluded from filter evaluation, the filter predicate will
  fail silently or return zero rows. Verify field is filterable before
  migration.

  ---
  sqlRevokeSessionsByHashes — UPDATE iam_sessions SET revoked_at WHERE 
  token_hash = ANY($1) AND tenant_id = $2

  Classification: EntityRepository BulkUpdate (N+6C). Same precondition as 
  above.

  Replaces the PostgreSQL ANY($1) array parameter with filter.In("token_hash", 
  hashes). Requires filter.In to exist in the filter package. If filter.In does
  not exist, this is a framework gap that must be filled before migration — add
  it to awo/filter, not to IAM.

  ---
  sqlInsertLoginAudit — INSERT INTO iam_login_audits ...

  Classification: EntityRepository (N+6C). Migrate.

  LoginAuditDefinition exists. LoginAuditImmutableGuard blocks BeforeUpdate and
  BeforeDelete only — BeforeCreate is unconstrained. Fields (tenant_id, user_id,
   service_account_id, event_type, ip_address, device_id, failure_reason,
  occurred_at) map to entity definition fields.

  Migration path: loginAuditRepo.Create(ctx, record). No transaction required —
  each audit event is independent. The repo handles RLS via context. Best-effort
   semantics preserved.

  Note: insertLoginAudit is called from multiple sites (login success, login
  failure, logout, session revoke). After migration, every call site becomes a
  repo.Create. The current helper function insertLoginAudit(ctx, tx, ...)
  signature changes — the tx parameter disappears.

  ---
  sqlLookupAPIToken — JOIN across iam_api_tokens and iam_service_accounts

  Classification: DatabaseQuerier (N+6D). Do NOT touch in N+6C.

  EntityRepository is per-entity. A JOIN across two entities has no
  representation in the repository abstraction. Decomposing into two sequential
  queries (fetch token by hash, then fetch service account by ID) would work
  functionally but changes the atomicity semantics and adds a round-trip to the
  auth hot path.

  This is a permanent DatabaseQuerier candidate. It is one of the primary
  reasons N+6D exists.

  ---
  sqlLoadRolePermissions — SELECT role_name, permission_id FROM 
  iam_role_permissions

  Classification: DatabaseQuerier (N+6D). Do NOT touch in N+6C.

  iam_role_permissions has no EntityDefinition. It is a global table with no
  tenant_id column and no RLS policy. EntityRepository requires an
  EntityDefinition and assumes tenant scoping. This table is categorically
  outside the EntityRepository contract.

  Called once at startup for CasbinEvaluator initialization. Performance is not
  a concern. Simplicity is. Keep as raw SQL wrapped in DatabaseQuerier.

  ---
  sqlLoadUserRoles — SELECT role_name FROM iam_user_roles WHERE tenant_id = $1 
  AND user_id = $2

  Classification: EntityRepository (N+6C). Migrate — with acknowledged 
  awkwardness.

  UserRoleDefinition exists and is registered. The query is a simple filter on
  (tenant_id, user_id). EntityRepository.Query with
  filter.And(filter.Eq("tenant_id", tenantID), filter.Eq("user_id", userID))
  returns []def.EntityRecord. Caller extracts record.GetString("role_name") from
   each.

  The awkwardness: the result type goes from []string to []def.EntityRecord
  requiring extraction. This is a minor caller-side inconvenience with no
  correctness risk, only a compile-time gap (wrong field name = runtime empty
  string, not compiler error).

  Transaction constraint: loadUserRoles currently runs inside the credential
  verification transaction. With migration, options are:

  - userRoleRepo.WithTx(tx) — preserves transaction membership
  - userRoleRepo.Query(ctx, ...) — opens independent transaction via pool

  The independent query is safer from an abstraction standpoint. RLS context is
  set from the context value. The login flow can commit its credential
  transaction first, then query roles independently. Roles are tenant-scoped via
   RLS; no cross-tenant leak is possible. The behavioral change (roles loaded
  outside the credential transaction) is acceptable — they were always
  committed-read-consistent anyway.

  ---
  Repository Suitability Review

  iam_user

  Suitability: Partial.

  For standard CRUD (admin creates user, updates status, lists users) — fully
  suitable. EntityRepository.Create fires UserPasswordHasher.BeforeCreate, which
   is exactly what should happen for user creation. EntityRepository.Update
  fires UserPasswordHasher.BeforeUpdate, which handles password change
  correctly.

  For authentication credential lookup — not suitable. password_hash is
  sensitive. Standard repository access cannot be used for login.

  For last_login_at update — not suitable in N+6C. Hook interference from
  UserPasswordHasher.BeforeUpdate makes the update path unsafe without hook
  bypass capability.

  Verdict: Create a UserRepository scoped to admin CRUD operations. Do NOT use
  for credential lookup or last_login_at updates. The authentication path must
  go through DatabaseQuerier.

  ---
  iam_user_role

  Suitability: Full.

  Simple join table entity. UserRoleDefinition is registered. UserRoleChangeHook
   fires after create/delete and revokes sessions — this hook should fire
  through the normal entity pipeline when an admin assigns or removes a role.
  EntityRepository.Create and Delete are correct. EntityRepository.Query for
  role loading in the login flow is workable with field extraction.

  Verdict: Migrate. Repository adds value: hook execution, permission
  enforcement, audit trail through standard pipeline.

  ---
  iam_login_audit

  Suitability: Full.

  Append-only entity. LoginAuditDefinition is registered.
  LoginAuditImmutableGuard defends against mutation through the hook pipeline —
  exactly the right mechanism. EntityRepository.Create is the only operation
  needed. No reads, no updates, no deletes.

  Verdict: Migrate. Repository is the correct abstraction. Immutability is
  enforced at the framework level, not the service level.

  ---
  iam_session

  Suitability: Partial.

  SessionDefinition exists. Session records are the SQL audit trail for human
  sessions; they are NOT the authoritative session store (Redis via SessionStore
   is authoritative). EntityRepository.Create for initial record, BulkUpdate for
   revoked_at, are both workable — subject to the BulkUpdate hook precondition.

  One tension: iam_session records are an audit trail for auth.Session objects
  managed by auth.SessionStore. The two representations (SQL and Redis) are
  parallel. Repository writes to iam_session are intentionally best-effort; they
   do not affect authentication correctness. This argues against adding
  lifecycle hooks to SessionDefinition that could fail and block audit writes.

  Verdict: Migrate Create and BulkUpdate. No hooks should be registered on
  SessionDefinition for the revocation path. Confirm SessionDefinition.Hooks is
  empty or hooks do not block.

  ---
  iam_api_token

  Suitability: Partial.

  For admin operations (create token, revoke token, list tokens) —
  EntityRepository is appropriate.

  For validation in the auth hot path — not suitable. Validation requires a JOIN
   with iam_service_accounts. Standard repository access cannot perform this
  join.

  Verdict: Create a repository for admin CRUD. The hot path stays in
  DatabaseQuerier.

  ---
  iam_role_permissions

  Suitability: None.

  No EntityDefinition. Global table. No tenant_id. No RLS. EntityRepository
  contract requires all three. This table does not belong in the repository
  tier.

  Verdict: DatabaseQuerier permanently.

  ---
  platform_tenant

  Suitability: Full, but out of scope for N+6C.

  Tenant is a platform entity managed by platform/tenant, not IAM. IAM reads
  tenant data through TenantResolver middleware and auth.ViewerContext. No
  direct SQL to tenant tables exists in IAM. No action needed.

  platform_organization

  Suitability: Full, but out of scope for N+6C.

  Same as tenant. Out of scope.

  ---
  Transaction Boundary Review

  Current state (after N+6B)

  AuthService owns all transaction lifecycles explicitly:

  Login:
    tx1 = DB.Begin()
      set_tenant_context
      lookupCredentials          ← pgx direct
      loadUserRoles              ← pgx direct (within tx1)
    tx1.Commit()
    Sessions.Store()             ← SessionStore
    tx2 = DB.Begin() [best-effort]
      set_tenant_context
      insertSessionRecord        ← pgx direct (within tx2)
      insertLoginAudit           ← pgx direct (within tx2)
      updateLastLoginAt          ← pgx direct (within tx2)
    tx2.Commit()

  Logout:
    Sessions.Delete()            ← SessionStore
    tx3 = DB.Begin() [best-effort]
      set_tenant_context
      revokeSessionByHash        ← pgx direct (within tx3)
      insertLoginAudit           ← pgx direct (within tx3)
    tx3.Commit()

  After N+6C (target)

  Credential verification transaction stays manual — raw pgx, no repos.
  Best-effort audit writes migrate to individual repository calls. Tenant
  context comes from context.Context (set by TenantResolver), not manual
  set_tenant_context calls.

  Login:
    tx1 = DB.Begin()
      set_tenant_context         ← still explicit (for credential lookup)
      lookupCredentials          ← pgx direct (stays raw)
      userRoleRepo.WithTx(tx1).Query(...)  ← OR: separate query after
  tx1.Commit()
    tx1.Commit()
    Sessions.Store()             ← SessionStore
    [best-effort, no transaction]
      sessionRepo.Create(ctx, ...)     ← repo opens own tx internally
      loginAuditRepo.Create(ctx, ...) ← repo opens own tx internally
      DB.Exec(sqlUpdateLastLoginAt)   ← still raw (hook issue)

  Logout:
    Sessions.Delete()            ← SessionStore
    [best-effort, no transaction]
      sessionRepo.BulkUpdate(...)      ← repo opens own tx internally
      loginAuditRepo.Create(ctx, ...) ← repo opens own tx internally

  Behavioral change: atomicity of best-effort audit writes.

  Currently, insertSessionRecord + insertLoginAudit + updateLastLoginAt are
  atomic within tx2. After N+6C, each is independent. If sessionRepo.Create
  succeeds but loginAuditRepo.Create fails, the session record exists without a
  corresponding audit event. This was always best-effort (neither failure
  affected authentication correctness), but the partial failure surface
  increases from 0 to 2 independent failure points.

  This is acceptable for the audit tier. If strict atomicity of audit writes is
  required, use WithTx across all repos within a single manually-opened
  transaction. The cleaner path: accept independent writes, increase
  observability (log each failure individually rather than once per
  transaction).

  Transaction ownership decision

  AuthService retains transaction ownership for the credential verification 
  transaction. This transaction is security-critical; no abstraction boundary
  should own it other than the service layer.

  Best-effort audit transactions are eliminated. Repos handle their own
  transactions internally. The best-effort semantics are preserved: call the
  repo, ignore errors (log them), continue.

  set_tenant_context fate

  After N+6C:
  - Still called manually inside the credential verification transaction (for
  sqlLookupCredentials)
  - Removed from audit path (repos handle via context)
  - Removed from loadUserRoles if that migrates to standalone repo call

  After N+6D (when DatabaseQuerier takes the credential transaction):
  - set_tenant_context disappears from service.go entirely — DatabaseQuerier
  handles it internally

  ---
  EntityRepository Interface Review

  WithTx(tx pgx.Tx) EntityRepository[T]

  Essential for N+6C. Without it, repos cannot participate in the credential
  verification transaction for loadUserRoles. The interface must support it. If
  driver.EntityRepository does not currently define WithTx, add it to the
  interface before N+6C begins.

  Implementation concern: contrib/pgx must call set_tenant_context internally
  when operating from a pool. When operating via WithTx, it must trust the
  caller has already set the context — or call it again (idempotent, safe).
  Document which behavior contrib/pgx implements.

  BulkUpdate(ctx, *filter.Filter, Patch) (int64, error)

  Required for session revocation by token_hash. Must NOT fire per-record
  BeforeUpdate hooks — this is the critical precondition. If BulkUpdate fires
  hooks, session revocation via EntityRepository is infeasible; the statement
  stays raw until DatabaseQuerier.

  Return value should be the count of updated rows. Callers can log zero-row
  updates for observability.

  Missing: BulkCreate

  Not needed for N+6C. Future consideration.

  Missing: Hook bypass option

  There is no mechanism to call repo.Update while bypassing lifecycle hooks.
  This gap is why sqlUpdateLastLoginAt cannot migrate in N+6C. If a hook bypass
  mechanism existed (e.g., repo.WithoutHooks().Update(...)), last_login_at could
   migrate. Do NOT add hook bypass in N+6C — it undermines the hook contract.
  Correct approach is DatabaseQuerier.

  Unnecessary: entity-specific methods

  Do not add IAM-specific methods to EntityRepository (e.g., GetByEmail,
  GetByTokenHash). These would couple the generic interface to IAM domain
  concepts. Residual special-case queries belong in DatabaseQuerier.

  ---
  Performance Review

  Additional allocations

  userRoleRepo.Query returns []def.EntityRecord instead of scanning directly
  into []string. Each EntityRecord allocates a map[string]any for its Data
  field. For a typical user with 2-3 roles, this is 2-3 additional map
  allocations per login. Negligible — login is not a hot path; it happens once
  per session.

  Extra queries

  No additional queries introduced. The migration is 1:1 — each SQL statement
  maps to one repository call. The credential verification transaction does not
  gain extra round-trips.

  Exception: if loadUserRoles is moved outside the credential transaction (Step
  6), the connection acquisition from the pool becomes a separate pool checkout.
   On a healthy pool, this is microseconds. Acceptable.

  Transaction overhead

  Current auditLogin holds one mini-transaction for three writes. After N+6C,
  two writes become standalone repo calls (two independent transactions), one
  write remains in a manual transaction. Net change: two additional transaction
  open/commit cycles, each a single round-trip. On a local PostgreSQL
  connection, this is ~1ms per transaction. For best-effort audit, unacceptable
  overhead is not defined — these were never latency-critical.

  Unnecessary abstractions

  filter.And(filter.Eq("token_hash", hash), filter.Eq("tenant_id", tenantID)) to
   replace a direct WHERE clause is more verbose but not slower — the predicate
  generates equivalent SQL. The abstraction adds compile-time type safety at the
   field-value boundary (partially — field names are still strings).

  ---
  Architectural Risks

  Critical

  C1 — BulkUpdate fires per-record hooks

  If contrib/pgx BulkUpdate invokes BeforeUpdate per row, session revocation via
   EntityRepository becomes O(N) in DB round-trips. For a user with 10 active
  sessions, that's 10 reads (to fetch prev records for UserPasswordHasher) + 10
  hook invocations + 1 bulk update. For a force-logout-all operation affecting
  1,000 users, this is catastrophic.

  Mitigation: verify before Step 5. If hooks fire, sqlRevokeSession* stays raw
  and becomes DatabaseQuerier in N+6D. No loss — scope reduction, not failure.

  ---
  High

  H1 — Sensitive field regression

  If, in any future refactor, someone replaces sqlLookupCredentials with
  userRepo.Get(ctx, id) or userRepo.Query(ctx, filter.Eq("email", email)), and
  the framework strips password_hash at the repository layer, login silently
  breaks — bcrypt.CompareHashAndPassword receives an empty hash and rejects all
  credentials.

  Mitigation: add a comment to sqlLookupCredentials documenting why
  EntityRepository cannot replace it. Enforce in code review. N+6D's
  DatabaseQuerier.LookupCredentials method signature returns typed (passwordHash
   string, ...) — making the intent explicit and testable.

  ---
  H2 — Constructor explosion

  New() gains three parameters in Step 2. With six parameters total, Wire DI
  graph becomes harder to audit. A transient dependency issue during wiring is
  hard to debug.

  Mitigation: group the three repos into a IAMRepositories struct:

  type IAMRepositories struct {
      Sessions  driver.EntityRepository[def.EntityRecord]
      Audits    driver.EntityRepository[def.EntityRecord]
      UserRoles driver.EntityRepository[def.EntityRecord]
  }
  func New(db *pgxpool.Pool, sessions auth.SessionStore, tokenCache cache.Cache,
   repos IAMRepositories) *Module

  Reduces constructor parameter count. Keeps N+6D migration cleaner (one struct
  field changes, not three).

  ---
  H3 — filter.In absent from awo/filter

  If filter.In does not exist, sqlRevokeSessionsByHashes cannot migrate in N+6C.
   The array-parameter version stays raw. This is a scope reduction, not a
  failure. The statement joins DatabaseQuerier.

  Mitigation: check awo/filter package before planning Step 5. If filter.In is
  absent, add it as a framework extension (Step 1 extended). Do not add
  IAM-specific workarounds.

  ---
  Medium

  M1 — Field name magic in EntityRecord extraction

  rec.GetString("role_name") is a runtime string lookup. A field rename in
  UserRoleDefinition would not produce a compiler error — it would silently
  return empty strings and every user would authenticate with zero roles, which
  Casbin would treat as having no permissions. Login would succeed but every
  subsequent authorization check would fail.

  Mitigation: add a unit test that asserts loadUserRoles returns non-empty
  results for a seeded user. This catches field name drift. Consider typed
  accessor helpers in the iam package:

  func roleNameFromRecord(r def.EntityRecord) string {
      return r.GetString("role_name")  // single point of change if field 
  renamed
  }

  ---
  M2 — WithTx RLS context ownership

  contrib/pgx may or may not call set_tenant_context when handling WithTx
  operations. If it doesn't, and N+6C retains WithTx calls, callers must
  remember to set it manually before the first repo operation on each
  transaction. This is an invisible invariant — violating it causes RLS to see
  no tenant, returning empty rows rather than an error.

  Mitigation: if contrib/pgx.WithTx does NOT set tenant context, document this
  prominently in the method's godoc. Alternatively, have contrib/pgx.WithTx
  always re-call set_tenant_context at the start of the first operation —
  idempotent and safe.

  ---
  M3 — Test double proliferation

  Three repo types (noop, spy, fail) need to implement the full
  EntityRepository[T] interface for each test scenario. As the interface gains
  methods (BulkCreate, BulkUpdate, WithTx, etc.), test doubles require updates.
  This is maintenance overhead.

  Mitigation: define a single baseNoopRepo that implements all methods as
  no-ops. Embed it in spy/fail variants that override only the methods under
  test. This is the standard Go test double pattern.

  ---
  Low

  L1 — Best-effort atomicity reduction

  Audit writes that were atomic in one transaction become three independent
  writes. In pathological scenarios (DB goes down between writes), a session
  record exists without a corresponding audit event, or vice versa. Audit tables
   are not operational — they are investigational. Inconsistency is tolerable
  for post-hoc analysis.

  Mitigation: none required. Document the behavior change in auditLogin and
  auditLogout godoc.

  L2 — queries.go shrinkage may cause confusion

  After N+6C, queries.go contains only five statements. Developers may wonder
  why five statements remain raw when the others migrated. Without context, this

  statements are intentionally non-migratable in N+6C and are targeted for N+6D
