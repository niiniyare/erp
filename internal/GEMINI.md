# Gemini Code-Assist Configuration for /internal

This directory contains the core application logic of the Awo ERP system, organized following the principles of Clean Architecture.

## Directory Structure & Responsibilities

-   `api/`:
    -   `design/`: The `goa` DSL files that define the API endpoints, request/response payloads, and services. This is the single source of truth for the API.
    -   `handlers/`: HTTP handlers (both `gin` handlers and `goa` service implementations). They are responsible for:
        -   Receiving and validating HTTP requests.
        -   Calling the appropriate domain service in `internal/core/{domain}`.
        -   Formatting the response (success or error) to the client.
        -   **Handlers should contain no business logic.**

-   `core/{domain}` (e.g., `core/tenant`, `core/user`): This is the core of the application. Each domain package contains:
    -   **Domain Models**: The primary business entities (e.g., `Tenant`, `User`).
    -   **Service Interface**: Defines the contract for the business logic (e.g., `tenant.Service`).
    -   **Service Implementation**: The concrete implementation of the business logic. It orchestrates data access by calling repository methods.
    -   **Repository Interface**: Defines the contract for data persistence (e.g., `tenant.Repository`). This interface is implemented in the `internal/repository` directory.

-   `repository/`: Contains the **implementations** of the repository interfaces defined in `core`. Its responsibilities are:
    -   Interacting with the database via the `db.Store` interface from `/db/sqlc/store.go`.
    -   Converting domain models (from `core`) to `sqlc`-generated models (from `db/sqlc`) before writing to the DB.
    -   Converting `sqlc` models to domain models after reading from the DB.
    -   Managing database transactions.

-   `platform/`: Contains implementations for external concerns like database connections, caching, and authentication middleware.

-   `shared/`: Common utilities and types used across the application (logging, errors, context management).

-   `workflows/`: Business workflow logic implemented using `temporal.io`.

## Key Principles & Data Flow

The application follows a strict one-way dependency flow: `Handlers` -> `Services` -> `Repositories` -> `Database`.

1.  **Dependency Inversion:**
    -   Services and Repositories are defined as interfaces within the `core/{domain}` packages.
    -   Services (in `core`) depend on Repository *interfaces*.
    -   Repository implementations (in `repository`) depend on the `db.Store` from `sqlc`.
    -   This keeps the `core` business logic independent of the database and other infrastructure.

2.  **Service Layer Responsibility:**
    -   The Service layer contains all business logic, validation, and rules.
    -   It is the only layer that should call the Repository layer.
    -   It also handles cross-domain logic and caching.

3.  **Repository Layer Responsibility:**
    -   The Repository layer is the only layer that directly interacts with the `db.Store`.
    -   Its primary job is data persistence and retrieval, including the mapping between domain and database models.

4.  **Handler Layer Responsibility:**
    -   The Handler layer is the entry point for all API requests.
    -   It should be as thin as possible, delegating all business logic to the Service layer.
    -   It implements the interfaces generated by `goa`.

5.  **Context Propagation:**
    -   The `context.Context` must be passed down through all layers, from Handlers to the database.
    -   It carries critical information like tenant ID, tracing data, and deadlines. The `db.Store` uses it to set the tenant for RLS.
